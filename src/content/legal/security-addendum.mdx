## 1. Purpose and Scope

This Security Addendum ("Addendum") is Exhibit C to the Master Services Agreement between Datum Technology, Inc. ("Datum") and Customer (the "MSA"). It describes Datum's information security program, the technical and organizational controls Datum maintains to protect the Services and Customer Data, and Datum's commitments regarding security certifications, vulnerability management, and incident response. Capitalized terms not defined herein have the meanings given in the MSA.

This Addendum applies to Datum's production infrastructure and management systems. It does not govern the security of Customer's own workloads, applications, or data transmitted over Datum's network infrastructure — those remain Customer's responsibility under the shared responsibility model described in Section 3.

## 2. Information Security Program

### 2.1 Program Overview

Datum maintains a written information security program ("Security Program") designed to protect the confidentiality, integrity, and availability of the Services and the Account Personal Data and Customer Data processed in connection with them. The Security Program is aligned with the SOC 2 Trust Services Criteria (Security, Availability, and Confidentiality) and is reviewed and updated at least annually or upon material changes to Datum's infrastructure or threat landscape.

### 2.2 Security Governance

* Datum's Security Program is owned by [Drew Raines, Head of Engineering] and reviewed at the executive level on a quarterly basis.

* Security policies covering access control, incident response, vulnerability management, data classification, and acceptable use are maintained in written form and made available to all Datum personnel.

* All Datum employees and contractors with access to production systems or Customer Data receive security awareness training upon onboarding and annually thereafter.

* Datum conducts periodic risk assessments to identify and prioritize security threats and maintains a risk register with documented remediation owners and timelines.

## 3. Shared Responsibility Model

Datum operates under a shared responsibility model for security. The division of responsibility between Datum and Customer is as follows:

| Security Domain | Datum Responsible | Customer Responsible |
| :---- | :---- | :---- |
| **Physical infrastructure security** | Data center physical access, hardware security, power and cooling | N/A — Customer has no physical access to Datum infrastructure |
| **Network infrastructure** | Datum's network fabric, routing, switching, BGP configuration, DDoS mitigation at infrastructure level | Customer's own network configuration, firewall rules, and traffic policies applied via Datum's management APIs |
| **Platform / management plane** | Management console security, API authentication, Datum software stack, OS patching on Datum-managed systems | Customer's use of management credentials; configuration of customer-controlled security policies |
| **Identity and access (Datum personnel)** | MFA enforcement, privileged access management, JumpCloud-based identity for all Datum personnel | N/A |
| **Identity and access (Customer users)** | Providing secure authentication mechanisms (SSO, MFA options) for Customer's management console access | Enforcing MFA and access controls for Customer's own Authorized Users; credential management |
| **Encryption in transit** | TLS 1.2+ on all management plane communications; encryption of data in transit across Datum's network fabric | Encryption of Customer's own application traffic where required by Customer's security requirements |
| **Encryption at rest** | Encryption of Account Personal Data at rest using AES-256 | Encryption of Customer's own data stored in Customer-managed storage |
| **Customer workloads and applications** | N/A — Datum provides network infrastructure, not application hosting | Security of Customer's own workloads, applications, containers, and VMs deployed on or routed through Datum's infrastructure |
| **Customer network traffic payload** | N/A — Datum does not inspect or access Customer traffic payload | Full responsibility for security and compliance of Customer's own traffic content |
| **Vulnerability management** | Patching and hardening of Datum's management plane, network software, and underlying infrastructure on Datum's defined cadence | Patching Customer's own systems and applications |
| **Incident response** | Detection and response to incidents affecting Datum's infrastructure; notification to Customer per MSA §7.3 | Response to incidents affecting Customer's own workloads or systems; cooperation with Datum investigations as needed |

## 4. Technical Security Controls

### 4.1 Encryption Standards

* Data at rest: AES-256 encryption for all Account Personal Data and Datum system data stored on Datum-managed infrastructure.

* Data in transit: TLS 1.2 minimum (TLS 1.3 preferred) for all management plane communications, API calls, and console access. TLS 1.0 and 1.1 are disabled.

* Encryption keys are managed via a dedicated key management service with automated rotation on a [90-day / annual] schedule. [CONFIRM WITH ENGINEERING]

### 4.2 Access Control

* Role-based access control (RBAC) is enforced across all Datum production systems, limiting access to Account Personal Data and infrastructure management functions to personnel with a documented operational need.

* Multi-factor authentication (MFA) is required for all Datum personnel accessing production systems, management consoles, and source code repositories. MFA is enforced via JumpCloud.

* Privileged access to production infrastructure requires approval via Datum's privileged access management process and is logged with tamper-resistant audit trails.

* Access rights are reviewed quarterly. Access is revoked within one (1) business day of employee or contractor termination, consistent with Datum's published Access Control Policy.

* Datum's identity management is centralized in JumpCloud, providing SSO, device trust, and directory services for all Datum personnel.

### 4.3 Network Security

* Datum's management plane is network-segmented from the customer data plane. Customer traffic does not traverse or have access to management infrastructure. [CONFIRM ARCHITECTURE WITH ENGINEERING]

* Firewall rules restrict inbound access to management systems to authorized IP ranges and authenticated sessions only.

* DDoS mitigation controls are implemented at the infrastructure level. [CONFIRM WITH ENGINEERING: describe actual mitigation mechanism and where it sits in the stack]

* BGP route security controls are implemented to protect against route hijacking and unauthorized route advertisements.

* Intrusion detection systems monitor management plane traffic for anomalous activity and generate alerts for human review.

### 4.4 Vulnerability Management

* Datum conducts automated vulnerability scanning of management plane systems and infrastructure on a [weekly] basis. [CONFIRM WITH ENGINEERING]

* Critical and high severity vulnerabilities (CVSS score 7.0+) are remediated within fourteen (14) calendar days of identification. [CONFIRM WITH TEAM — see Schedule 1] Medium severity vulnerabilities are remediated within [30] days. [CONFIRM WITH ENGINEERING]

* Datum conducts penetration testing of production infrastructure [annually] using a qualified third-party security firm. Executive summaries of penetration test findings and remediation status are available to Customers upon request under NDA. [CONFIRM CADENCE WITH ENGINEERING]

* Open source and third-party components incorporated into the Datum platform are tracked in a software bill of materials (SBOM) and monitored for CVEs via automated tooling. [CONFIRM SBOM TOOLING AND COVERAGE WITH ENGINEERING]

* Datum participates in responsible disclosure and maintains a security disclosure contact at security@datum.net.

### 4.5 Logging and Monitoring

* Security-relevant events on management plane systems are logged to a centralized SIEM with tamper-resistant storage retained for a minimum of [12] months. [CONFIRM WITH ENGINEERING]

* Automated alerts are configured for unauthorized access attempts, anomalous API call patterns, privilege escalation events, and bulk data access.

* Datum's on-call engineering team monitors production infrastructure on a 24/7 basis via automated alerting.

* Access logs for Account Personal Data are retained in accordance with the DPA retention schedule.

### 4.6 Endpoint Security

* All Datum-issued devices used to access production systems are enrolled in Datum's mobile device management (MDM) program via JumpCloud, enforcing disk encryption, screen lock, and remote wipe capability.

* Endpoint detection and response (EDR) software is deployed on all Datum-issued devices with access to production environments.

* Personnel are prohibited from accessing production systems from unmanaged personal devices.

## 6. Incident Response

### 6.1 Incident Response Plan

Datum maintains a written incident response plan ("IRP") that defines detection, classification, containment, eradication, recovery, and post-incident review procedures. [CONFIRM IRP DOCUMENT EXISTS AND LAST TABLETOP EXERCISE DATE WITH ENGINEERING] Key elements include:

* A designated incident response team with defined roles and escalation paths.

* Automated detection via SIEM alerting, supplemented by customer-reported incidents submitted to support@datum.net or security@datum.net, consistent with Datum's published Incident Response Policy.

* Incident classification aligned to the P1-P4 priority levels defined in the SLA (Exhibit A).

* A 72-hour notification commitment to Customer for any confirmed Security Incident affecting Account Personal Data, per MSA §7.3 and DPA §3.3. This is distinct from, and narrower than, Datum's general public Incident Disclosure Policy, which uses a conditional disclosure model for vulnerabilities not involving Account Personal Data. [CONFIRM BOTH POLICIES ARE INTENDED TO COEXIST AS DRAFTED]

* Post-incident review and root cause analysis for all P1 incidents, with findings shared with Customer within five (5) business days of resolution.

### 6.2 Reporting a Security Issue

Customers who believe they have identified a security vulnerability in Datum's platform or who wish to report a suspected security incident should contact Datum at security@datum.net. Datum will acknowledge receipt within one (1) business day and will provide a preliminary assessment within five (5) business days. Datum participates in coordinated disclosure and will not pursue legal action against researchers acting in good faith under Datum's responsible disclosure guidelines.

## 8. Third-Party and Supply Chain Security

### 8.1 Sub-processor Security

Datum's sub-processors with access to Account Personal Data (listed in DPA Schedule 3) are evaluated for security posture prior to onboarding and on an annual basis thereafter. Evaluation criteria include: SOC 2 Type II or equivalent certification; data processing agreement terms; incident notification commitments; and access minimization practices. Datum will notify Customer of material changes to the sub-processor list per DPA §5.2.

### 8.2 Open Source and Third-Party Software Security

Datum's platform incorporates open source and third-party components used to operate Datum's own infrastructure and orchestration tooling. These components are not directly accessed by Customers and are not Third-Party Software for purposes of the MSA. Datum maintains a software bill of materials (SBOM) for material platform components and monitors for known vulnerabilities via automated CVE scanning. [CONFIRM SBOM TOOLING AND COVERAGE WITH ENGINEERING] Security patches for critical vulnerabilities in third-party components are applied within the timeframes specified in Section 4.4. Customers may request Datum's current SBOM summary under NDA.

### 8.3 Infrastructure Hardware

Datum's network infrastructure is software-defined, built on Datum's open network cloud platform and delivered across Datum's infrastructure providers (GCP, Servers.com, and NetActuate). Core routing and traffic management is handled through Envoy, an open-source distributed proxy, with web application firewall protection provided by Coraza. [CONFIRM WITH ENGINEERING]

## 9. Customer Security Obligations

While Datum maintains the controls described in this Addendum for its own infrastructure, Customers are responsible for the security of their own use of the Services. Customer security obligations under the MSA include:

* Maintaining the confidentiality and integrity of Customer's account credentials and API keys. Datum will not ask for Customer passwords.

* Enforcing MFA for all Authorized Users accessing the Datum management console.

* Promptly revoking access for Authorized Users who no longer require it.

* Configuring Customer's own firewall rules, network policies, and access controls through Datum's management APIs in accordance with Customer's security requirements.

* Ensuring Customer's own workloads and applications deployed on or routed through Datum's infrastructure comply with applicable security standards and regulations.

* Promptly notifying Datum at security@datum.net upon discovering any suspected unauthorized access to Customer's Datum account or any security vulnerability in the Services.

* Complying with Datum's Acceptable Use Policy with respect to network traffic content and workload types.

## 10. Updates to This Addendum

Datum will update this Addendum from time to time to reflect: improvements to Datum's security program; changes in certification status (including SOC 2 Type II completion); updates to the data residency table as new Service Regions become active; and changes in the third-party and hardware stack. Datum will provide Customer with at least thirty (30) days' prior written notice of any update that materially reduces the protections described herein, consistent with MSA §7.5. Non-material updates (including certification additions, new Service Region listings, and contact detail changes) take effect upon posting to datum.net/security or upon written notice to Customer.
